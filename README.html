项目概述

XFT 是一个命令行工具，为 企业软件销售团队 生成产品模块推荐。给定一家中国企业的名称，系统会：

  1. 从 DuckDB 企业画像库 读取该公司的结构化档案（行业、规模、招聘、分支机构、资质等）
  2. 加载 YAML 场景配置，其中定义了 7 个可推荐的产品模块和每个模块下的判断指标
  3. 对每个指标，按配置的评估策略进行判断——可能是确定性规则、LLM 推理、或两者混合
  4. 在证据不足时，按需触发 Web 搜索 补证（非预先搜索所有指标）
  5. 汇总得分，选出最优推荐模块，输出 result.json 和 report.md
设计理念：配置驱动、证据优先、懒加载 Web。业务人员改 YAML 即可调优推荐逻辑，无需动代码。

核心原理

推荐流水线

推荐引擎是一个三阶段的有向无环图（DAG），由 LangGraph StateGraph 编排：

data_gather → recommend → save
节点职责关键文件
data_gather 从 DuckDB 读取企业画像，根据指标 data_sources 加载本地证据 nodes/data_gather_node.py
recommend 评估每个模块→标签→指标；开启 Web 时创建 lazy resolver，指标需要补证时才搜索 evaluator.py + web_resolver.py
save 写入 result.json、report.md、调试日志、LLM trace、Web trace 等全部产物 nodes/save_node.py

结果层级

推荐结果的层级结构：

Module
推荐模块 → Label
业务标签 → Indicator
判断指标 → Score
分数 & 接受度

评分机制

每个指标的判断结果有四种：matched（命中）、possible（可能）、unknown（未知）、not_matched（未命中）。指标得分汇聚到标签，标签汇聚到模块，最终按 (-score, -attributes_number, module_id) 选出得分最高的模块，再根据 acceptance_policy 门槛判定接受度（高 / 中高 / 低）。

结果值默认指标分默认标签分含义
matched1030证据足够，判断命中
possible515有线索但证据不足
unknown00证据不足，无法判断
not_matched00证据显示不命中

关键设计决策

手动 DI，无框架

组件直接实例化依赖，通过工厂函数（get_ai_client()、build_provider()）支持测试替换。LangGraph 是唯一编排点。

Lazy Web 补证

Web 搜索不出现在图节点中，而是在每个指标计算时按需触发。避免不必要的搜索，减少成本和噪声。

配置审计追踪

每次运行写入 config_manifest.json，记录每个配置文件的路径和 SHA256 哈希，确保输出可完整复现。

单例模式

settings、_ai_client、_engine、display 为进程级单例，适合 CLI 短期生命周期。

包边界

src/xft/web/        ← 不依赖 pipeline
src/xft/cache/      ← 不依赖 pipeline
src/xft/utils/      ← 不依赖 pipeline
src/xft/warehouse/  ← 不依赖 pipeline
src/xft/ai/         ← 不依赖 pipeline
src/xft/pipeline/   ← 消费以上所有包

DuckDB 数据模型

企业画像库的核心是 company_profile 表（Gold 层），推荐主线还会读取 5 张明细表作为指标本地证据：

表来源 JSON推荐用途
company_profileinfo.json + 多源聚合企业基本信息、行业、标签、经营范围
recruitmentsrecruit_message.json招聘岗位标题、城市、来源
branchesbranch.json分支机构分布
qualificationsquery_qualification.json企业资质
outbound_investmentsinvestor_info.json对外投资
key_personnelinfo.json + staff.json关键人员

Web 补证数据流（lazy）

Web 搜索不再作为独立图节点，而是在 recommend 阶段按指标延迟触发：

  1. 读取场景 web_search.yaml，过滤启用的 provider
  2. 当前指标计算时，先取得本地证据；rule / hybrid 先跑规则
  3. 根据 web_search.when 判断是否搜索（always / insufficient / rule_not_matched / never）
  4. 只对需要补证的指标执行固定查询和可选自动查询
  5. 同一轮运行内复用重复查询的 provider 结果，但按指标分别落 trace
  6. 过滤非目标公司或非指标相关的结果
  7. 可选：通过 crawl4ai 抓取搜索结果页面的完整 Markdown 正文
关键约束：llm_web 无实际 Web 证据时直接返回 unknown，不会在空证据下调用 LLM，防止模型编造。

配置体系

系统有五层配置，从上到下逐步细化：

层级位置作用
1. 环境变量.env → settings.pyAPI 密钥、LLM 模型名、缓存 URL。支持 SM4 加密
2. 场景入口scenario.yaml场景 ID、名称、引用模块和 Web 配置路径
3. 全局评分modules.yamlindicator/label 分值、接受度门槛、模块目录引用
4. 模块定义modules.d/*.yaml（7 个文件）每个模块的标签、指标、规则、prompt、Web 策略
5. Web providerweb_search.yaml搜索 provider 列表、超时、结果数量限制

模块配置 DSL

一个完整的模块 YAML 示例：

modules.d/个税管理.yamlmodule_id: 个税管理
module_name: 个税管理
priority: 40
base_score: 0
labels:
  - label_id: 薪酬规模
    label_name: 薪酬规模
    min_matched_indicators: 1
    indicators:
      - indicator_id: 个税相关招聘
        indicator_name: 个税相关招聘
        evaluator: rule
        standard: 招聘标题包含社保、个税或薪酬
        data_sources:
          - type: table
            table: recruitments
            field: title
            op: text_contains
            keywords:
              - 社保
              - 个税
              - 薪酬
      - indicator_id: 财报合并范围
        indicator_name: 财报合并范围
        evaluator: llm
        standard: 企业存在多法人主体或合并报表需求
        prompt: 判断企业是否可能存在多法人主体集团化管理需求
        evidence_hints:
          - 分支机构数量
          - 对外投资企业
          - 股东结构
        web_search:
          when: insufficient
          effect: llm_evidence
          fixed_queries:
            - "{company_name} 集团 分子公司"
          auto:
            enabled: true
            max_queries: 2
            intent: 判断企业是否为多法人集团

唯一性约束

module_id 全局唯一 · 同一模块下 label_id 唯一 · 同一标签下 indicator_id 唯一

四种评估器

每个指标通过 evaluator 字段指定判断策略：

evaluator触发条件调用 LLM？Web 角色
rule 结构化字段明确，例如招聘标题、资质、分支机构 否 可选，最多补到 possible
llm 需要综合文本和证据推理 是 可选，通常证据不足时补证
hybrid 先用规则判断硬证据，再让 LLM 处理模糊判断 可选 可选，推荐的增强方式
llm_web 必须依赖公开网页才能判断 是 必须，Web-first

Rule — 确定性规则

直接从 company_profile 字段读取：

evaluator: rule
standard: 企业标签包含高新技术企业
rule:
  source_field: labels
  op: contains
  value: 高新技术企业

从 DuckDB 明细表取证据：

evaluator: rule
standard: 招聘标题包含销售或渠道
data_sources:
  - type: table
    table: recruitments
    field: title
    op: text_contains
    keywords:
      - 销售
      - 渠道
操作符含义
exists字段存在且非空
contains字符串或列表包含某个值
contains_any包含列表中的任一值
== / !=等于 / 不等于
> / >= / < / <=数值比较

Hybrid — 规则优先 + LLM 补充

推荐用于"本地证据优先，LLM 补充判断"的指标：

evaluator: hybrid
merge_policy: rule_first
standard: 企业具备高新技术企业、专精特新、科技型中小企业等资质
rule:
  source_field: labels
  op: contains_any
  value: [高新技术企业, 专精特新, 科技型中小企业]
prompt: 判断企业是否具备科技型企业资质。
merge_policy逻辑
rule_first规则命中直接 matched，不调用 LLM；规则未命中再调用 LLM
llm_confirm规则给候选信号，LLM 确认；如 LLM 否定则降级
require_both规则和 LLM 都命中才 matched

LLM Web — 必须依赖公开网页

evaluator: llm_web
standard: 企业公开信息显示存在海外客户、海外业务或跨境服务
prompt: 请判断企业是否存在海外业务，只能基于证据判断，不得编造。
web_search:
  when: always
  effect: llm_evidence
  fixed_queries:
    - "{company_name} 海外业务"
    - "{company_name} 海外客户"
  auto: false
  max_results: 5
约束：llm_web 必须配置 web_search。没有实际 Web 证据时直接返回 unknown，不会在空证据下调用 LLM。

选择顺序

  1. 能用本地字段或明细表判断 → rule
  2. 有本地信号但需要解释或补证 → hybrid
  3. 有本地证据，需要综合推理 → llm
  4. 只有公开网页才可能判断 → llm_web

判断推荐是否可用

  1. result.json 的 Module、AcceptanceResult、Conclusion
  2. logs/{run_id}.log 是否能解释每个指标为什么命中、未命中或调用 Web/LLM
  3. report.md 是否能解释推荐理由
  4. indicator_evidence.json 是否有足够证据支撑命中指标
  5. 如启用 LLM，检查 llm_metrics.json 是否有失败调用
  6. 如启用 Web，检查 web_trace.json 中查询词和结果是否与指标相关

调优流程

模块调优顺序

  1. 先审计配置：uv run xft scenario audit config/recommender/xft
  2. 只跑目标模块，关闭 LLM 和 Web，先验证本地规则：--no-llm --module 个税管理
  3. 开启 Web，观察哪些指标真的需要补证：--with-web --module 个税管理
  4. 开启 LLM debug，检查 prompt 和证据是否足够：--with-web --llm-debug --module 个税管理
  5. 精调单个指标：--with-web --llm-debug --module 个税管理 --indicator 个税相关招聘

优先看哪些文件

logs/{run_id}.log           ← 开头有"调优建议摘要"
indicator_evidence.json     ← 证据是否支撑指标
web_trace.json              ← 查询词和搜索结果是否相关
llm_calls.jsonl             ← LLM 推理过程
label_result.json           ← 全部判断明细

日志中需要优先处理的告警

告警含义处理
unknown 指标证据不足，无法判断检查 data_sources 或添加 Web 补证
无证据指标完全没有本地证据确认 data_sources 配置正确
Web 未搜索需要补证但未触发检查 --with-web 和 web_search.when

常见问题治理

推荐结果不准

先看 label_result.json 定位误命中指标，再看 indicator_evidence.json 确认证据来源。优先调整 data_sources.keywords 或 rule。

Web 证据噪声大

固定查询词必须包含指标词。检查哪些指标配了 when: always。抽查 web_trace.json。

LLM 成本过高

冒烟用 --no-llm。能写成 rule 的指标不要写成 llm。hybrid 用 rule_first 可跳过 LLM。

接受度过高/过低

调整 modules.yaml 的 acceptance_policy.levels 门槛和结论文案。

搜索词原则

好的查询词 = {company_name} + 指标词 + 业务场景词：

yaml (推荐)fixed_queries:
  - "{company_name} 个税 薪酬 招聘"
  - "{company_name} 社保 个税 管理"
yaml (避免)fixed_queries:
